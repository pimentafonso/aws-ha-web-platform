# Security

This document explains each security control in the platform and why it is there. _Sections are filled in as the stacks are built._

## Reporting a vulnerability

This is a personal reference project. If you find a security issue, please open a private security advisory on this repository rather than a public issue.

## Controls

| Area | Control | Why |
|---|---|---|
| Identity | GitHub OIDC role assumption for CI, no stored access keys. Each environment's deploy role trusts only `repo:pimentafonso@350777569/aws-ha-web-platform@1456449290:environment:<env>` (GitHub's immutable subject format, which pins the account and repository IDs as well as their names) with audience `sts.amazonaws.com`, for sessions of at most two hours | There is no AWS key in GitHub to leak or rotate. A token from a fork, another repository or another environment is refused by STS, and the credentials it buys expire on their own. |
| Identity | Least-privilege IAM: the service's task role only allows `rds-db:connect` as `notes_app` on one instance. Separate execution roles for the service (Valkey token) and the migration task (database master secret), each limited to one repository, one log group and one secret. KMS decrypt only through Secrets Manager. The GitHub deploy role can only drive its environment's stacks through that environment's CloudFormation execution role, push to one ECR repository, run the migration task, sync one bucket prefix and invalidate CloudFront; it cannot delete stacks or read secrets. The execution role can create IAM roles only if they are named `<env>-*` and carry a permissions boundary it cannot change, and is denied the audit trail and the other environment's resources | If the API container is compromised, its credentials can reach the notes data and nothing else: no other AWS API, no master password. A leaked deploy session cannot call AWS APIs beyond deploying, and no template, even a malicious one, can create a role more powerful than the boundary. Review on `main` remains the main control over what CloudFormation is asked to build (see the README's CI/CD design decisions). |
| Network | Application and data tiers in private subnets. The ALB security group admits only the CloudFront origin-facing prefix list, and the listener forwards only requests carrying a secret `X-Origin-Verify` header (generated by Secrets Manager); anything else gets a 403. The app tasks accept only the ALB | Other CloudFront distributions share those addresses, so the header proves the request came through this distribution, where WAF has already checked it. CloudFront adds the header from a dynamic reference to the secret, so it is not in any template. |
| Network | Data subnets have no default route; app subnets reach the internet only outbound through NAT | A database or cache cannot be reached from, or send data to, the internet even if a security group is misconfigured. |
| Network | No subnet auto-assigns public IPv4 addresses | Only the NAT Gateways (Elastic IPs) and the ALB are publicly addressable, and only by explicit design. |
| Network | S3 gateway endpoint policy limited to `s3:GetObject` on the Region's ECR layer bucket | The endpoint serves image pulls only, so it cannot be used to copy data out to an arbitrary bucket. |
| Network | Interface endpoints (prod) for ECR, CloudWatch Logs and Secrets Manager; their security group allows only HTTPS from the VPC CIDR and has no egress | Secret retrieval, image pulls and log delivery stay on the AWS network. |
| Network | Dev NAT instance: no SSH key or inbound SSH (SSM Session Manager only), IMDSv2 required, encrypted disk, security group allowing only HTTPS in from the VPC and HTTPS out | A cheaper NAT should not become the easiest way into the VPC. Limiting it to port 443 also stops workloads using it for anything other than HTTPS. |
| Detection | VPC flow logs (all traffic) in prod, to a KMS-encrypted log group with 365-day retention. Off in dev (`LoggingMode=minimal`) | Lets me investigate rejected or unexpected connections after the fact. Only the account's CloudWatch Logs service can use the key, and the delivery role can only write to that one log group. Dev carries only test traffic, so I accept the gap there to keep it free. |
| Network | Database and cache security groups accept 5432 and 6379 only from the app security group, and have no egress rules | Only the application tasks can open a connection to the data tier. Anything else in the VPC, including the NAT instance, is refused. |
| Data | One customer-managed KMS key for the data tier (RDS storage and backups, Performance Insights, ElastiCache at rest, both secrets), rotated yearly; logs use a separate key. The static bucket uses SSE-S3, because its files are public web content | Reading the data needs both the service permission and `kms:Decrypt` on this key, and every use of the key is logged in CloudTrail. When prod takes a final snapshot, the key is retained so the snapshot can still be restored. |
| Data | TLS required to PostgreSQL (`rds.force_ssl=1`, server certificate verified against the RDS CA) and to Valkey (in-transit encryption `required`) | Credentials and query results never cross the network in plaintext, even inside the VPC. |
| Secrets | The RDS master password is generated and rotated by RDS in Secrets Manager (`ManageMasterUserPassword`). The Valkey AUTH token is generated by Secrets Manager and passed to ElastiCache through a dynamic reference. Both secrets are encrypted with the data key, and ECS will inject them into tasks | No secret ever appears in a template, a parameter file, the stack's parameters or the repository. The database password changes every 7 days without me handling it. The Valkey token is not rotated automatically yet. |
| Transport | ACM certificates, TLS from viewer to CloudFront and from CloudFront to ALB. The ALB listener uses HTTPS with `ELBSecurityPolicy-TLS13-1-2-2021-06` when given a certificate, and a CloudFormation rule refuses to deploy prod without one. Viewers: HTTP redirects to HTTPS, minimum `TLSv1.2_2021`, HSTS from the managed security-headers policy. ACM renews every certificate itself | Dev has no domain, so it runs HTTP from CloudFront to the ALB and uses CloudFront's default certificate for viewers. Template rules stop prod deploying without a domain, the origin certificate and the viewer certificate, so prod is TLS end to end and never sends the origin header in plaintext. |
| Data | IAM database authentication for the API (15-minute tokens, TLS required); the database master password is used only by the migration task | Nothing long-lived to leak from the service, and the master password's 7-day rotation never interrupts running tasks. |
| Edge | AWS WAF on the CloudFront distribution in prod: Amazon IP reputation list, a per-IP rate limit (1,000 requests per 5 minutes), the common rule set and known bad inputs | Common attacks and floods are dropped at the edge before they reach the ALB or cost Fargate time. AWS keeps the managed groups up to date. Blocked and counted requests are logged to a KMS-encrypted log group in us-east-1. |
| Edge | Static bucket: Block Public Access, ACLs disabled, no website endpoint, HTTPS required, readable only by this distribution through origin access control | The only way to read the files is through CloudFront, where TLS and WAF apply. |
| Detection | CloudTrail: one multi-Region trail for the account (management events, global services), with log file validation, to a versioned, KMS-encrypted audit bucket that is retained on stack deletion | Every API call in the account, in any Region, is recorded, and digest files prove the logs were not changed. Only CloudTrail and GuardDuty can use the key, each for its own resources. |
| Detection | GuardDuty on CloudTrail, VPC flow and DNS logs. Findings are exported to the audit bucket, and medium or higher findings are emailed through a KMS-encrypted SNS topic. Optional plans are listed explicitly as disabled; Runtime Monitoring for Fargate is a parameter | Compromised credentials, crypto-mining and calls from known-bad addresses are flagged without my having to write the rules. Disabling plans explicitly means none can switch on through an account default and add charges unnoticed. |
| Detection | Access logs for the ALB, CloudFront and the static bucket in a per-environment bucket that only those log services may write to, HTTPS only | A request can be traced from the edge to the task, using the ALB trace id that the API also logs. |

## What is not in this repository

No AWS account IDs, access keys, secrets or real domain names are committed. Account-specific values are passed in at deploy time through environment variables or GitHub repository variables.
